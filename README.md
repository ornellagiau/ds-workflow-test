# DS workflow test: cost-free design system pipeline

Figma (Turm Foundations: tokens) → GitHub (docs, code, daily checks) → Storybook on GitHub Pages (team view) → Claude (reads the repo).

**State (28 Oct 2026):** the real Turm color tokens (176) with their descriptions are documented. Two components exist: **Link** (colors from the Turm tokens, provisional CSS names) and **Button** (plain hex values on purpose, the demo for the sync status). The repo is **public for now** and holds real Turm color token names, values and descriptions. It is meant to become private later, then Pages needs another home.

## Setup (about 15 min)
1. Create a **public** repo on your personal GitHub account (GitHub Pages is free only for public repos). Mind what it contains: Turm color tokens and descriptions, no other internal SZ content.
2. Upload this folder's contents to the repo (drag and drop in the GitHub web UI works, or `git push`).
3. In the repo: **Settings → Pages → Source: GitHub Actions**.
4. The workflow runs on every push and once a day. Your Storybook appears at `https://<user>.github.io/<repo>/`.
5. In Claude: connect the **GitHub** connector and point it at the repo. `CLAUDE.md` tells it where to look.

## Flow
- **Token or description change in Turm:** you get the email from the daily check → open a chat with Claude and say "check Turm" → Claude compares and exports `tokens/turm-colors.json` → you commit → the pages update.
- **Doc change:** edit the `.mdx` → commit → Storybook updates → ask Claude to run `figma/sync-descriptions.js` in Figma.

## Sync check and Code Connect
Two things connect the Figma components with the code: the **sync check** (finds drift) and **Code Connect** (shows the real code in Figma).

**Which files take part**
| File | Role |
|---|---|
| `figma/component-map.json` | The mapping. Per component: the Figma component set id, which Figma property is which code prop, and what the sync check compares (`sync`). |
| `scripts/check-sync.mjs` | The sync check. Runs in the daily workflow (via `npm run build-all`) and writes the generated page **Status/Sync status**. |
| `src/components/*/*.figma.ts` | The Code Connect templates. One per component, next to the code. |
| `figma.config.json` | Tells Code Connect where the templates are (`src/**/*.figma.ts`). |
| `.github/workflows/storybook-pages.yml` | The job `deploy` runs the sync check, the job `code-connect` publishes the templates on every push to `main`. |
| `scripts/fixtures/figma-sync.json` | Test data in the shape of Figma's web API, so the check can run without Figma. |
| `src/components/Link/Link.tokens.css` | The color values (light and dark) that the check uses to resolve the CSS variables of Link. |

**What the sync check compares.** It compares each Figma component with the **real implementation**, not with the contract. The contract is a starting document, so a drift between the contract and the code is not reported.
- **Properties:** the Figma properties against the properties the Code Connect template reads, and against the props in the component's `.jsx` (the mapping `properties` in the component map).
- **Variants:** every Figma variant option must have a CSS rule (a modifier class, or a state such as `:hover`). A CSS modifier without a Figma variant, and a Figma option that is not in the map, are reported.
- **Colors, per variant and per mode:**
  - **Link:** text color, underline color and width, focus ring color and width, for every Size, Emphasis and State, in **light and dark**.
  - **Button:** background, border color and text color, in light.
- **Layout and typography:** only where `"layout": true` is set in the map. That is Button today (padding, corner radius, stroke width, font family, weight and size). Link's typography is driven by Figma variable modes and is not compared yet.

**Dark mode.** Figma's web API gives the colors of the file's default mode (light). So the sandbox file has the frame **"Link dark (sync check)"** on the page "Link Turm". It holds one instance of every Link variant, and the Turm collection "Color Semantics" is set to **dark** on that frame. Only the mode is swapped, no variable is changed. The instances are named like the variants (`Size=S, Emphasis=Primary, State=Idle`), the check matches them by name. If a variant is added to the Link, add its instance to this frame too. The check does not compare dark mode, and says so on the page, when the frame is missing, when its instances have no layers, or when Figma returned light colors for it.

**How the CSS is read.** The check has a small CSS engine. It reads class selectors, the descendant combinator, `:hover`, `:focus-visible`, `:active` and attribute selectors such as `[aria-disabled="true"]`. It applies the cascade by specificity and order, expands the shorthands (`border`, `outline`, `padding`, `background`), and resolves `var(--x)` from the token CSS (`:root` is light, `[data-theme="dark"]` is dark). It does **not** read `@media` blocks, nested rules, the combinators `>`, `+`, `~`, and `:not()`, `:is()`, `:where()`, `:has()`. What it skips is listed on the page under "Not read by the check".

**Reading the Sync status page**
- **✅ in sync:** nothing differs. **⚠️ n differences:** see the table. **❓ could not check:** Figma or the node could not be read.
- A row says what differs, in which mode and for which variants, with the Figma value and the code value side by side. Colors are hex values. "none" means no color, for example a transparent underline.
- Button shows one difference on purpose (padding 11/31 in Figma, 10/30 in code). It is the demo of what drift looks like. Do not fix it.
- Differences are only shown on the page. They do not fail the build and do not send an email.

**Code Connect.** A template shows the code snippet for a component instance in Figma's Dev Mode. The CLI publishes the templates (`npm run figma:connect`) with the secret `FIGMA_ACCESS_TOKEN` (scope `file_code_connect:write`). Each template starts with a comment that holds the Figma node url. A template maps Figma properties to props: for Link, `Link Text` is `children`, `Size` is `size`, `Emphasis` is `emphasis`, and the state `Disabled` is `disabled`. Hover, focus and pressed are CSS, not props. The icons are a placeholder (`<Icon />`), because there is no Icon component yet. `npx figma connect parse` checks that the templates are valid. When a Figma property changes, update the `.figma.ts` file, never the template in Figma.

**Add a component**
1. Build the component in the sandbox file, with the variant property names as in Figma.
2. Add the component (`.jsx`, `.css`, `.mdx`, `.stories.jsx`, `.figma.ts`). The `.mdx` needs a `figma-description:set:` line.
3. Add an entry to `figma/component-map.json`: `figmaSetId`, `properties`, `variants` (can be empty), and `sync` with `elements` (CSS classes), `layers` (Figma layers), `axes` (Figma option to CSS class or state) and `checks`. Copy the Link entry.
4. For dark mode, add a frame with instances and the dark mode, and put its id in `darkFrameId`.
5. Run the check on the test data: `FIGMA_FIXTURE=scripts/fixtures/figma-sync.json node scripts/check-sync.mjs` (replace the fixture with real values for the new component).

**Descriptions go the other way.** The `figma-description` lines in a component `.mdx` are copied into Figma by `figma/sync-descriptions.js`, which Claude runs in Figma. A description can have several lines. The doc card in Figma must be a frame named `doc:<node id>` with a text named `description`.

## Daily Turm check
The workflow also watches the real **Turm Foundations** file in Figma, so you can see how often the library changes.

**What it does**
- Every day (06:00 UTC, GitHub often starts it a few hours late) and on every push to `main`, the workflow runs `scripts/check-turm.mjs`.
- It reads the Turm file from Figma, read-only: the last edit and the version history.
- **Log:** it saves `status/turm-log.json`. The workflow commits it only when something changed. The log holds only timestamps and anonymous version ids, no names and no labels, because the repo is public.
- **Page:** the Storybook page **Status/Turm updates** shows the last edit, changes in the last 7 and 30 days, the average per week and the latest changes.
- **Email:** the workflow opens an issue **"Turm changes"** assigned to the repo owner and adds one comment per event. GitHub emails you. Events: tracking started (first run), Turm changed, the check failed (once, not every day), the check works again.
- It counts every save in the version history, not only token changes. The current state of the file (its version id) is counted too, because Figma adds saves to the version list only with a delay. The same id is counted once.
- If the version history is not available (missing token scope), it counts at most one change per day.
- **What it cannot show:** it knows *when* Turm was saved, never *which tokens* changed. For that, ask Claude for the exact token check.

**When the email arrives**
1. Open a chat with Claude in the project and say "check Turm".
2. Claude reads the tokens through the Figma connector, compares them with the Turm data file in `tokens/`, and tells you exactly which names, values or descriptions changed.
3. Commit the updated files.

**Setup**
- Files: `scripts/check-turm.mjs` and `.github/workflows/storybook-pages.yml`.
- Secret `FIGMA_ACCESS_TOKEN`: a Figma token with exactly these scopes: `file_content:read`, `file_versions:read`, `file_code_connect:write` (the last one is for the Code Connect publish step). Scopes cannot be changed afterwards: to change them, create a new token and replace the secret. Tokens expire, so note the expiry date. When it expires, the page says "Not checked" and you get an email.
- The workflow file grants itself `contents: write` (log commit) and `issues: write` (issue). Only if the commit step fails with 403: **Settings → Actions → General → Workflow permissions → Read and write**.
- First test: **Actions → Publish Storybook → Run workflow**. Expected: the issue "Turm changes", a commit "Turm log: update" and the page Status/Turm updates.

**If something looks wrong**
| Sign | Cause | Fix |
|---|---|---|
| Page says "Not checked: Figma answered 403 or 404" | The token has no access to the Turm file, or it expired | Create a new read-only token and replace the secret |
| Page says "version history was not available" | The token lacks the file versions scope | Add the scope to the token; until then at most one change per day is counted |
| The issue gets a comment but no email | GitHub email notifications are off, or the mail is in spam | GitHub → Settings → Notifications: turn on email for "Participating, @mentions and custom". The issue is assigned to the repo owner, so it counts as participating. Check spam. |
| Log not updated although Turm changed | The log commit was skipped because the repo changed at the same moment | The next run adds it |

**Good to know**
- The times come from Figma. Scheduled runs can be late, so they are not the time of the change.
- The repo is public for now. That is why the issue text and the log stay generic. When the repo becomes private, this can be extended.
